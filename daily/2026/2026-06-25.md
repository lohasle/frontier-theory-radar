## 4. 今日深挖论文

- **一句话本质：** 把'训练数据配方'当成 Agentic 模型的第一设计变量——单一 benchmark 训出来的 agent 会在换任务时崩，而系统化的跨任务数据策展才是泛化能力的来源。
- **底层问题：** Agentic LM 大幅扩展了 AI 的应用面，但'如何为广泛能力的 agent 策展训练数据'几乎是黑箱。现有开源项目(SWE-Smith 偏软件工程、SERA、Nemotron-Terminal)各自只面向单一 benchmark，于是训练数据与评估数据同构，跨任务泛化无从谈起。
- **理论根基：** '数据配比即能力边界'——模型会朝训练分布偏移，若训练任务面窄，泛化能力就被封顶。OT-Agent 把它形式化为'数据 recipe'问题：哪些任务源、多少配比、什么难度分布，才能让 agent 在未见任务上保持能力。
- **工程实践映射：** 直接对应三类痛点：(1) Agent 过拟合——单任务 SFT/RL 换场景即退化；(2) 评估污染——训练 benchmark 与评估 benchmark 同源导致虚高；(3) 数据成本——开放 recipe 让团队不必从零摸索。可类比对齐阶段的基础/指令/偏好三段式配比，但这里升级到'多任务 Agent 行为轨迹'的配比。
- **新命题 / 新方法 / 新证据：** 新命题是'跨多类 Agentic 任务的泛化可以被一条开放的、可复现的数据 recipe 显著提升'；方法是完全开放的数据策展流水线(data curation pipeline)；证据来自与多个单 benchmark 方案(SWE-Smith 等)的跨任务对照。作者延续 OpenThoughts 系列(此前在推理数据上有较强可信度)。
- **研究位置：** 处于'方法+对照实验'阶段，介于配方提出与大规模外部复现之间。它的价值是把'agent 训练数据'这个大家都在做但很少公开方法的问题，提升为'可对标、可复现'的工程维度。
- **工程可验证性：** 即使无官方代码，也能自建最小验证：选定 2-3 个异质 agent benchmark(如一个软件工程类、一个工具调用类、一个检索类)，构造'单任务训练'与'多任务混合训练'两组，测各组在留出任务上的保持率，直接量化'数据配方'对泛化的影响。这是本周可落地的实验。
- **趋势关联：** 与 ai-agent、rag-knowledge、coding-agent、data-engineering 四条线交汇，是'2026 年重心从训出一个大模型转向训出一个能跨任务泛化的 agent'这条主线的代表，建议纳入未来 1-3 个月的 Agent 训练数据趋势线。
- **长尾价值：** 即便具体 recipe 不通用，'跨任务数据配比'这一方法论也会沉淀为 Agent SFT/RL 的 checklist——每次新增任务源时都要问'它会让模型在旧任务上退化多少'。
- **启发：** 单任务 SOTA 是陷阱，跨任务保持率才是 agent 可用性的真实指标——评估谁更强时，先看它在'没见过的任务'上的退化幅度。

## 7. 启发

### 对系统设计的启发
把'训练数据配方'当成 Agentic 系统的第一设计变量：与其在单一任务上刷到 SOTA，不如在异质任务集上保证跨域保持率——前者是 demo，后者才是产品。

### 对 AI Agent 工程化的启发
InSight 的'把示教切分为带标签 primitive、运行时按指令组合'，是所有 agent(不止机器人)的通用抽象：技能=可命名、可复用、可组合的原子动作。自建 agent 时先建 primitive 库，再做组合调度，比一上来训端到端长程策略更可控。

### 对团队研发流程的启发
OT-Agent 说明'agent 训练数据'正在从各家私房菜走向可公开对标的 recipe；研发流程应增加一道'数据配方评审'——每次新增任务源都要测它对旧任务的退化影响。

### 对企业落地的启发
评估 agent 强弱时，单任务成功率会骗人；应把'跨任务保持率'(在未见任务上的退化幅度)作为上线门槛指标，避免 demo 过拟合。

### 对个人学习路径的启发
今天的阅读顺序建议：先读 OT-Agent 把握'数据配方即能力边界'主线，再读 InSight 学具身 agent 的 primitive 分解，最后扫 FLUX3D 与次梯度界把握生成侧与理论侧长尾。

### 对未来 6-12 个月技术趋势的启发
趋势重心会从'谁模型更大'转向'谁更会做跨任务数据配方与自主技能获取'——模型红利见顶后，数据 recipe 与 skill library 是新的增长点。
